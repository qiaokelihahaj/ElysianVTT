# 数据模型草案

## 1. 术语说明

- PL：玩家主体。
- PC：PL 所操控的对象。
- GM：全局主持与裁决主体。
- OB：默认只读观察主体。

本草案中的“玩家”都指 PL。PC 只用于表示被 PL 控制的实体或角色。

## 2. 设计目标

权限系统必须有数据落点，否则重启、断线、授权撤销、审计追踪都会失去基础。数据模型的目标不是追求表越少越好，而是让以下关系被清晰持久化：

1. 谁是谁。
2. 谁拥有哪个角色。
3. 谁能控制哪些 PC。
4. 谁能看哪些场景和日志。
5. 谁能改骰子、谁改过、为什么改。
6. 谁在什么时间段拥有过什么权限。

## 3. 建模原则

- 身份数据和授权数据分离。
- 主体与可控制对象分离。
- 授权记录与审计记录分离。
- 会话数据与永久身份数据分离。
- 可见性数据和控制数据分离。

这样做的原因是，权限系统的“当前状态”与“历史记录”不是同一个问题。

## 4. 核心实体

### 4.1 User

表示登录主体。

建议字段：
- id
- displayName
- email 或 loginName
- passwordHash 或第三方身份标识
- status
- createdAt
- updatedAt

说明：User 是系统账号层，不等于 GM / PL / OB 的业务语义。一个 User 可以在不同会话中拥有不同会话态，但通常会绑定一个主角色模板。

### 4.2 Role

表示业务角色模板。

建议枚举：
- GM
- PL
- OB
- AUDITOR（可选）

说明：
- GM 是全局裁决者。
- PL 是玩家主体。
- OB 是观察主体。
- AUDITOR 可作为后续扩展的审计查看角色。

### 4.3 Session

表示一次登录会话或 Socket 会话。

建议字段：
- id
- userId
- accessTokenId 或 tokenVersion
- roleSnapshot
- expiresAt
- revokedAt
- createdAt
- lastSeenAt
- ipAddress
- userAgent

用途：
- 绑定身份。
- 追踪在线状态。
- 做 token 失效和重连恢复。

### 4.4 Scene

表示一个场景容器。

建议字段：
- id
- name
- state
- visibilityPolicy
- currentEngineId
- createdBy
- createdAt
- updatedAt

### 4.5 Entity

表示场景中的实体。

建议字段：
- id
- templateId
- sceneId
- ownerUserId
- controllerScope
- type
- stateJson
- transformJson
- resourcesJson
- activeEffectsJson
- isAlive
- createdAt
- updatedAt

说明：
Entity 是被操控对象，而不是玩家主体。PC 可以作为 Entity 的一种业务表现，但不能和 PL 混用。

### 4.6 PermissionGrant

表示一次授权授予记录。

建议字段：
- id
- grantedByUserId
- grantedToUserId
- capability
- scopeType
- scopeId
- sceneId
- expiresAt
- reason
- createdAt
- revokedAt
- revokedByUserId

用途：
- 记录临时授权。
- 记录委托范围。
- 便于撤销和审计。

### 4.7 AuditEvent

表示审计事件。

建议字段：
- id
- actorUserId
- actorRole
- eventType
- subjectType
- subjectId
- sceneId
- tick
- beforeJson
- afterJson
- reason
- visibility
- createdAt

用途：
- 记录骰子改值。
- 记录权限变化。
- 记录场景管理动作。
- 记录 GM 裁决。

### 4.8 DiceRoll

表示一次掷骰。

建议字段：
- id
- sceneId
- sourceEntityId
- rolledByUserId
- rollType
- inputExpr
- rawResultJson
- finalResultJson
- overriddenByUserId
- overrideReason
- overrideType
- createdAt

说明：
- overrideType 建议区分 SYSTEM 与 MANUAL。
- 如果最终结果被改写，必须保留 rawResultJson。

### 4.9 LogEntry

表示日志记录。

建议字段：
- id
- sceneId
- tick
- namespace
- level
- visibility
- message
- metaJson
- createdAt

说明：
- visibility 决定可见范围。
- metaJson 可放结构化信息，但要经过过滤。

### 4.10 PermissionSnapshot

表示一次会话或主体当前可用权限的快照结果。

建议字段：
- id
- sessionId
- userId
- roleSnapshot
- version
- controllableEntitiesJson
- visibleEntitiesJson
- capabilitiesJson
- currentSceneIdsJson
- issuedAt
- expiresAt
- refreshedAt

用途：
- 作为 IntentRouter 的高频判定输入。
- 作为广播分组和前端感知的缓存结果。
- 作为授权变更后快速失效和重建的依据。

说明：
- PermissionSnapshot 不是权限真相，而是可缓存的判定结果。
- 授权变更、会话重连、角色切换后应重新签发快照。

## 5. 关系设计

### 5.1 User 与 Session

- 一个 User 可以有多个 Session。
- 一个 Session 只能对应一个 User。
- Session 过期或撤销后，Socket 必须重新认证。

### 5.2 User 与 Entity

- 一个 User 可以拥有多个 Entity。
- 一个 Entity 只能有一个默认 owner。
- 一个 Entity 可以被多个授权主体临时控制，但最终必须以 scope 限制。

### 5.3 User 与 PermissionGrant

- 一个 User 可以授予多个权限。
- 一个 User 也可以收到多个权限。
- 每条授权都应该有过期时间或撤销记录。

### 5.4 Scene 与 Entity

- 一个 Scene 包含多个 Entity。
- 一个 Entity 通常隶属于一个 Scene。
- 场景切换时需要保证 Entity 的 controllerScope 不被错误继承。

### 5.5 Scene 与 LogEntry / AuditEvent

- 日志和审计事件都应绑定 Scene。
- 这样可以按场景过滤，也方便回放与排错。

### 5.6 Session 与 PermissionSnapshot

- 一个 Session 可以对应多个快照版本，但同一时刻只应有一个有效快照。
- 快照应绑定到 Session 和 User，便于会话重连后恢复。
- 快照过期或被撤销后，Socket 必须重新认证或刷新权限。

## 7. 索引建议

- sessions(user_id, revoked_at, expires_at)
- entities(scene_id, owner_user_id, is_alive)
- permission_grants(granted_to_user_id, scope_type, scope_id, revoked_at, expires_at)
- permission_snapshots(session_id, version, expires_at)
- audit_events(scene_id, actor_user_id, event_type, created_at)
- dice_rolls(scene_id, source_entity_id, created_at)
- log_entries(scene_id, visibility, level, created_at)

索引目的：
- 快速判断当前主体能控制什么。
- 快速查找某场景的授权和审计记录。
- 快速检索某场景的日志和骰子历史。

## 8. 备选方案

### 8.1 全部放在 JSON 文本里
优点：实现快。
缺点：查询、过滤、索引、审计都很难。

### 8.2 所有权限只放内存
优点：运行快。
缺点：重启即丢失，无法审计。

### 8.3 完全关系化建模
优点：可查询、可审计、可扩展。
缺点：建表更多，前期实现稍重。

### 8.4 选择当前方案的原因
当前项目已经需要处理授权、日志和骰子审计，纯 JSON 或纯内存都太脆弱。采用以关系表为核心、JSON 字段承载状态快照的混合方案，最适合当前阶段。

## 9. 与权限逻辑的对应关系

- GM 的全域权限来自 role + permission_grants。
- PL 的默认控制权来自 user_roles + entities.owner_user_id。
- OB 的观察权来自 role + scene visibility policy。
- 骰子改值来自 audit_events + dice_rolls。
- 会话认证来自 sessions。
- 权限快照来自 sessions + permission_snapshots。

## 10. 结论

数据模型的重点不是“多建几个表”，而是把主体、对象、授权、审计和可见性分开。只要这五层分开，PL 和 PC 的概念就不会混，后续实现也更容易稳定。
